프로젝트 안에서 사이클별 · 모듈별 보기

프로젝트는 항상 최상위 기준이다. 지금의 프로젝트 그룹은 그대로 두고, 그 안쪽만 전체 작업 / 사이클별 / 모듈별로 갈아끼운다. 전체 작업이 기본값이고 지금 화면과 완전히 같다. 전환은 섹션 헤더 오른쪽 드롭다운 한 곳. 하위 묶음은 프로젝트 헤더보다 확실히 가볍게 그려서 "프로젝트가 크고 그 안이 나뉜다"가 한눈에 읽히게 했다. 사이클/모듈을 안 쓰는 프로젝트는 하위 묶음 없이 지금처럼 평평하게 나온다(아래 OPS 프로젝트).

구현 메모 — 화면 쪽
  • 바깥 구조는 안 건드린다. groupItemsByProject가 돌려주는 ProjectGroup은 그대로 두고, 그 items를 한 번 더 쪼개는 함수(splitByCycle / splitByModule)만 더한다. 전체 작업 축은 "쪼개지 않음"이라 지금 코드 경로 그대로다.
  • 하위 묶음 순서는 진행 중 → 예정 → 지난 → 없음 고정. 진행 중이 여럿이면 종료일 임박순. 모듈은 날짜가 없으니 진행 중 → 완료 → 없음, 그 안에서는 이름순.
  • 하위 묶음이 하나뿐이면 헤더를 아예 안 그린다 — 사이클을 안 쓰는 프로젝트에 "사이클 없음" 한 줄만 덧붙는 건 순수한 노이즈다.
  • 접힘 상태 collapsedGroups(Set)에 하위 묶음 id까지 넣되, 축이 다르면 키를 분리한다 (cycle:<id> 같은 접두어). 안 그러면 축을 오갈 때 엉뚱한 게 접힌 채로 남는다.
  • 프로젝트를 접으면 하위 묶음까지 통째로 숨는다. "모두 접기" 버튼은 프로젝트 단만 접는다 — 하위까지 함께 접으면 다시 펼 때 두 번 일해야 한다.
  • 선택한 축은 설정에 저장한다(SettingsDto에 sidebar_group_axis 한 줄).
검색·필터가 켜져 있을 때 — 검색 결과가 하위 묶음까지 나뉘면 3개 찾은 게 세 묶음에 하나씩 흩어져 오히려 찾기 어렵다. 검색이나 필터가 걸려 있는 동안에는 하위 묶음을 끄고 프로젝트 안에 평평하게 보여주는 쪽을 권한다. (이건 기존 "접힌 그룹이 검색 결과까지 숨긴다" 문제와 같은 계열이다.)
모듈은 작업 하나가 여러 개에 속할 수 있다 — 사이클은 작업당 최대 1개지만 모듈은 N개다. 목업 2번 줄 가운데를 보면 '토큰 만료 안내 추가'가 같은 프로젝트의 두 모듈에 동시에 나온다. 버그가 아니라 Plane의 모델이지만, 하위 묶음 카운트를 다 더하면 프로젝트 헤더의 숫자보다 커진다. 권장: 중복을 그대로 두고 카드에 겹사각형 칩(2)으로 "다른 모듈에도 있음"을 알린다 — Plane 웹과 같은 동작이라 사용자가 이미 아는 규칙이다. 프로젝트 헤더 카운트는 중복을 뺀 실제 작업 수로 유지한다.
진행률 링이 두 단이 된다 — 프로젝트 헤더의 4/9와 하위 묶음의 4/7이 나란히 보인다. 둘 다 "내게 할당된 작업 기준"이어야 말이 된다. 사이클 전체 진행률(팀 전원)을 하위에 쓰면 "내 목록엔 2개인데 링은 12개"가 되어 두 숫자가 서로 다른 것을 세게 된다. 하위 링은 작게(12px) 그려 프로젝트 링과 위계를 나눴다.
데이터 비용 — 이 기능의 진짜 무게 — Plane 공개 API의 work-items 목록 응답에는 cycle/module이 없다 (IssueSerializer에 그 필드가 없어 expand=cycle도 통하지 않는다). 프로젝트마다 cycles/·modules/로 목록을 받고, 다시 각각의 cycle-issues/·module-issues/로 소속을 받아야 한다. 줄이는 방법: ① 축을 고른 뒤에 처음 요청한다 — 전체 작업만 쓰는 사용자는 비용이 0이다, ② 사이클은 진행 중 + 다음 것만 먼저 받고 지난 사이클은 펼칠 때 받는다, ③ 소속 정보는 작업 목록보다 훨씬 덜 바뀌므로 갱신 주기를 길게(예: 10분) 따로 가져간다.
단계를 나눈다면 — 1단계로 사이클별만 내보내는 걸 권한다. 사이클은 작업당 1개라 중복 문제가 없고, "이번 스프린트에 뭐가 남았나"라는 실제 질문에 바로 답한다. 모듈은 중복 규칙까지 정리해야 하니 2단계로 미룰 수 있다. 드롭다운에는 처음부터 세 항목을 다 두되 모듈별을 나중에 켜도 UI는 그대로다.
