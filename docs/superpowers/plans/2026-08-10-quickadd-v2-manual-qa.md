# 빠른 추가 v2 — 릴리스 전 수동 확인 목록

- 대상 브랜치: `feat/quickadd-v2` (계획: `2026-08-10-quickadd-v2.md`)
- 작성 근거: 전체 브랜치 최종 리뷰(2026-08-11)

## 왜 이 목록이 필요한가

이 브랜치는 **한 번도 앱으로 실행된 적이 없다.** 구현·리뷰 전 과정이 코드 판독으로만
진행됐다. 자동 검증이 커버하는 범위는 다음이 전부다:

- `pnpm exec tsc --noEmit` — 배선의 타입 정합성 (`pnpm build`는 타입 검사를 하지 않는다)
- `pnpm test` 176개 — **순수 로직만**. 상태 전이, 프로젝트 이름 매칭, 담당자 배치.
- `cargo check` — Rust 컴파일

테스트는 렌더링·이벤트 배선·포커스·레이아웃에 **한 줄도 닿지 않는다**. vitest가 node
환경으로 돌고 jsdom/happy-dom이 설치돼 있지 않기 때문이다. 즉 "핸들러가 실제로 걸렸는가",
"포커스가 어디로 가는가", "660px 안에 들어오는가"는 사람이 눌러봐야만 알 수 있다.

실제로 이 브랜치에서 나온 결함 중 **타입 검사와 테스트를 모두 통과한 채 발견된 것**이
여럿이다 — 담당자 목록 요청 레이스, `Ctrl+Enter` 담당자 오적용, Esc 포커스 유실 등.

1~5번은 릴리스 전 필수로 본다.

## 필수

### 1. 담당자·값 오적용 (최종 리뷰 C1/I1 수정 확인)

컴팩트 레이아웃에서:

1. 담당자 칩에 포커스를 두고 `Enter`로 팝오버를 연다.
2. `↓`로 이동하며 `Space`로 **3명**을 지정한다. 팝오버는 열린 채로 남아야 한다.
3. 그 상태에서 `Ctrl+Enter`.
4. 등록된 항목을 Plane에서 열어 **담당자가 3명 그대로인지** 확인한다.

이어서 우선순위 칩에서 팝오버를 열고 `↓`로 다른 값에 커서만 올린 뒤 `Ctrl+Enter` →
**등록된 우선순위가 원래 값인지** 확인한다. (시작일·마감일·상태도 같은 경로다.)

수정 전에는 담당자 3명 중 2명이 말없이 사라지고, 커서가 놓인 값이 확정된 채 등록됐다.

### 2. 담당자 행 넘침 (I2 수정 확인 — CSS 구조만 검증됨, 눈으로 봐야 함)

실제 워크스페이스에서 **표시 이름이 가장 긴** 프로젝트를 골라 한눈에 보기를 켠다.

- 기본 상태에서 칩 4개 + `+N`이 660px 안에 들어오는가.
- `Ctrl+클릭`으로 **6명**을 지정했을 때 오른쪽 끝 칩과 "6명 지정됨" 힌트가 창 밖으로
  잘리지 않는가. (지정된 사람은 설계상 무조건 인라인으로 올라오므로 칸 수를 넘는다.)
- `+N` 버튼 자체가 찌그러져 숫자를 못 읽게 되지는 않는가.

### 3. 레이아웃 전환과 초안 보존

1. 빠른 추가에 제목·설명을 입력하고 담당자/상태/우선순위/시작일/마감일을 **모두
   기본값이 아닌 값**으로 바꾼다.
2. 창을 열어둔 채 설정에서 레이아웃을 바꿔 저장한다.
3. 확인: 창이 즉시 갈아끼워지는가 · **다섯 필드 값과 제목·설명 글이 전부 그대로인가** ·
   창 폭이 540↔660으로 바뀌고 높이가 내용에 맞는가 · 설명 입력칸이 접히고 토글도
   꺼진 상태로 일치하는가.
4. 반대 방향으로 한 번 더.
5. 그다음 곧바로 `Ctrl+Enter`로 등록해 **전환 전 값 그대로** 올라가는지 확인한다.

### 4. 한눈에 보기의 날짜 클릭

날짜 글자(`2026-08-11(화)`)를 클릭한다.

- OS 달력이 뜨는가. 창 밖으로 잘리지 않는가.
- 날짜를 고르면 값과 프리셋 표시가 갱신되는가(프리셋 밖 날짜면 세 버튼이 모두 꺼져야 한다).
- 뜨지 않으면 개발자 콘솔의 예외를 확인한다 — `showPicker()`에 방어가 없다.

### 5. 클릭 후 타이핑 (I4 수정 확인)

제목을 절반쯤 치다가 **마우스로** "긴급"을 클릭하고, 그대로 키보드로 제목을 이어 친다.

- 글자가 제목 칸에 들어가는가.
- 담당자 칩 클릭 후, 날짜 프리셋 클릭 후, `‹ ›` 스테퍼 클릭 후에도 각각 확인한다.
- **키보드로** 세그먼트를 고른 경우(`←`/`→`로 이동 후 `Enter`)에는 포커스가 그 행에
  남아 있어야 한다 — 이어서 `←`/`→`가 계속 동작하는지 확인한다.

## 권장

### 6. 프로젝트 검색

드롭다운을 열고 각각 확인한다.

| 입력 | 기대 |
|---|---|
| 부분 일치 (`자`) | 이름 중간에 걸려도 남고 그 글자가 강조된다 |
| 초성 (`ㄷㅈ`) | 초성으로 걸린다 |
| 영문 대소문자 (`pl`) | 대소문자를 가리지 않는다 |
| 없는 이름 | `일치하는 프로젝트가 없습니다` |

- 개수 표시가 검색 전 `N개`, 검색 중 `2/10` 꼴로 바뀌는가.
- `↑↓` 이동, `↵` 선택, `Esc` 닫기.
- **`Esc` 직후 바로 타이핑했을 때 제목 칸에 들어가는가** (I3 수정 확인).
- 스크롤바가 두 겹으로 나오지 않고 키보드 힌트 줄이 잘리지 않는가.

### 7. `+N` 팝오버

- 열기 / 재클릭으로 닫기 / `↑↓` 이동 / `↵` 선택(단독 지정 + 닫힘 + 제목 포커스)
- `Esc`로 닫으면 포커스가 `+N`으로 돌아오는가.
- 접힌 마지막 한 명을 `Ctrl+클릭`으로 지정했을 때 팝오버가 스스로 닫히는가.
- 팝오버가 카드 오른쪽 밖으로 삐져나가지 않는가.

### 8. 담당자 목록 레이스

- 프로젝트 A를 고르고 **응답이 오기 전에** 즉시 B로 바꾼다 → 담당자 행에 B의 멤버가
  뜨는가. (A의 목록이 B 이름표를 달고 남으면 안 된다.)
- 드롭다운에서 **이미 선택된 프로젝트를 다시** 골라도 담당자 행이 채워지는가.
- 네트워크를 끊고 프로젝트를 바꿔 실패시킨 뒤, 다른 프로젝트를 거쳐 돌아오면 다시
  요청하는가.

### 9. 설명 토글

두 레이아웃 각각에서: 열기/닫기 · 여러 줄 입력 시 창 높이가 따라 자라는가 · 닫았다 다시
열었을 때 글이 남아 있는가 · 등록 후 접히는가.

### 10. 사이드바 "+" 버튼

프로젝트별 "+"로 프로젝트를 지정했을 때 두 레이아웃 모두 프로젝트 라벨과 담당자 행이
갱신되는가.

### 11. 연속 등록

등록 성공 후 필드가 기본값으로 돌아가고 **프로젝트·멤버 목록은 유지**되는가. 바로 두 번째
항목을 올릴 수 있는가.

### 12. 테마

라이트/다크 양쪽에서 새 CSS(`.seg-track`, `.person`, `.date-stepper`, `.dd-search`,
`.dd-foot`, `<mark>` 강조)의 대비가 읽히는가.

### 13. 경계 데이터

프로젝트가 0개 / 1개일 때 · 멤버가 1명일 때(휠 순환이 꺼진다) · 프로젝트가 30개 이상일 때
드롭다운 스크롤.

## 알려진, 고치지 않은 것들

최종 리뷰에서 "그대로 출하"로 판정한 것 중 눈에 띌 수 있는 것들:

- **`+N` 팝오버에 `Space` 다중 토글이 없다.** 컴팩트 담당자 팝오버에는 있다. 키보드만
  쓰면 접힌 멤버는 단독 지정만 가능하고, 다중 지정은 `Ctrl+클릭`(마우스)뿐이다.
- **`+N` 팝오버는 바깥을 클릭해도 닫히지 않는다.** 컴팩트 팝오버와 프로젝트 드롭다운도
  같으므로 앱 전체 문법과는 일치한다. 고친다면 셋을 함께.
- **한눈에 보기의 설명 토글은 열려 있는 `+N` 팝오버를 닫지 않는다.** 컴팩트의 설명 칩은
  먼저 닫는다.
- **한눈에 보기에는 임의 날짜를 키보드로 지정할 경로가 없다.** `PgUp/Dn` 스텝으로만
  도달한다. 컴팩트 팝오버에는 포커스 가능한 날짜 입력칸이 있다.
- **`Esc`로 창을 닫는 것은 제목 입력에 포커스가 있을 때만 동작한다**(기존 규칙). 한눈에
  보기는 포커스가 세그먼트에 머무는 시간이 길어 체감 빈도가 오른다.
- **로드 실패 직후 "같은" 프로젝트를 곧바로 다시 골라도 담당자를 재시도하지 않는다.**
  다른 프로젝트를 거쳐 오면 재시도된다. 요청 폭주 방지와의 의도된 트레이드오프다.
