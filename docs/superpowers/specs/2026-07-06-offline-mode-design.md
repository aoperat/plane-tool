# 오프라인 모드 & 재연결 동기화 — 설계 스펙

- 날짜: 2026-07-06
- 상태: 사용자 승인 대기

## 목적

Plane 서버가 꺼져있거나 네트워크가 끊겨도 **직전에 보던 데이터를 계속 보고**,
**이슈 생성/수정/댓글 등 모든 쓰기 작업을 계속할 수 있게** 한다. 서버가
복구되면 밀린 변경을 자동으로 서버에 반영하고, 그 사이 다른 곳(Plane 웹 등)
에서 같은 항목이 바뀐 경우에는 자동으로 덮어쓰지 않고 사용자가 직접 병합
화면에서 선택하게 한다.

## 핵심 설계 결정

1. **전체 쓰기 작업을 오프라인 큐잉 대상으로 한다** — 이슈 생성, 상태/우선
   순위/담당자/날짜 변경, 댓글 작성, 삭제 등 전부. 부분 지원은 "이건 왜 안
   되지" 혼란만 늘린다.
2. **로컬 저장은 JSON 스냅샷/큐 방식**으로 한다 — SQLite 등 새 의존성 없이
   기존 `tauri-plugin-store` 패턴을 그대로 확장한다. 개인용 도구 규모의
   데이터양(N+1 프로젝트 조회 결과)에 JSON 파일 이상의 구조가 필요 없다.
3. **큐는 "기록 후 재생"(mutation log) 방식**이다. 기존 커맨드가 이미
   필드 단위 호출 구조(`updateStatus`, `updatePriority` 등)라서, 재생 순서를
   지키기만 하면 별도의 상태-diff 병합 로직 없이 마지막 변경이 자연히 남는다.
4. **재연결 감지는 기존 `assign_tick` 백그라운드 폴링에 편승**한다. 사용자가
   아무것도 하지 않아도 복구 시 자동으로 동기화가 시작된다.
5. **충돌은 자동 해결하지 않는다.** 큐에 넣던 시점의 서버 `updated_at`과
   재생 시점의 실제 `updated_at`이 다르면 자동 적용을 멈추고 수동 병합
   화면으로 넘긴다 — 조용히 덮어써서 남의 변경을 날리는 것보다 안전하다.

## 아키텍처 개요

```
[Plane 서버] <--HTTP--> [Rust: plane_api.rs]
                              │
                       (성공/실패 판정)
                              │
        ┌─────────────────────┴─────────────────────┐
        │                                             │
   성공 시 캐시 갱신                           네트워크 실패 시 큐에 적재
        │                                             │
[cache.json]  <-- 읽기 --  [sidebar/editmodal 프런트]  --> [pending-queue.json]
        │                                             │
        └──────────────── 재연결 감지(백그라운드) ───────┘
                              │
                     큐 재생(replay) + 충돌 검사
                              │
                     충돌 있으면 → conflicts.json → 수동 병합 화면
```

## 읽기 경로 — 로컬 캐시

- `fetch_sidebar_data`(`src-tauri/src/commands.rs`) 성공 시 응답 전체(이슈·
  프로젝트 목록)와 `cached_at` 타임스탬프를 `cache.json`에 스냅샷으로 저장
  (매번 덮어씀).
- 호출 실패(네트워크 오류) 시 `cache.json`을 로드해 반환하고, 프런트엔드는
  기존 footer 에러 표시 대신 "오프라인 · 마지막 동기화 HH:MM" 배지를 보여준다.
- 앱을 재시작해도 `cache.json`이 있으면 서버 연결 전에 먼저 이 스냅샷을
  화면에 그려서, 지금처럼 "재시작하면 아무것도 안 보임" 문제를 없앤다.

## 쓰기 경로 — 오프라인 큐

**저장 파일**: `pending-queue.json`, 배열, 각 항목:

```json
{
  "id": "uuid",
  "kind": "create_issue | update_field | create_comment | delete_issue | ...",
  "targetId": "실제 이슈 ID 또는 로컬 임시 ID",
  "payload": { "...": "기존 커맨드 인자 그대로" },
  "baseUpdatedAt": "충돌 비교용 서버 updated_at, create는 null",
  "queuedAt": "timestamp"
}
```

- 쓰기 커맨드가 네트워크 오류(connection refused, timeout 등)로 실패하면
  즉시 에러를 던지는 대신 위 형태로 큐에 적재하고, 캐시(`cache.json`)에도
  낙관적으로 반영해 화면에 바로 보이게 한다("동기화 대기" 표시).
- **네트워크 문제가 아닌 실패(4xx 검증 에러 등)는 큐잉하지 않고 지금처럼
  즉시 실패로 사용자에게 보여준다** — 그렇지 않으면 절대 성공 못 할 요청이
  큐에 영원히 쌓인다.
- **임시 ID**: 오프라인 중 quickadd로 만든 새 이슈는 `local-<uuid>`를 임시
  ID로 부여해 캐시에 추가한다. 같은 세션에서 이 이슈에 댓글을 달거나 필드를
  바꾸면 해당 큐 항목의 `targetId`도 임시 ID를 그대로 참조한다.
- **같은 필드 여러 번 변경**: 오프라인 중 우선순위를 3번 바꿔도 별도 병합
  없이 순서대로 큐에 쌓이고, 재생 시 순서대로 적용하면 자연히 마지막 값만
  남는다.

## 재연결 감지 & 재생

- 기존 `assign_tick`(`src-tauri/src/lib.rs`, 60초 폴링)에 "직전 tick 실패
  여부" 상태를 추가. 실패 → 성공으로 전환되는 순간을 복구 이벤트로 보고
  동기화를 트리거한다. 오프라인 중에는 tick 주기를 15~20초로 당겨 복구를
  더 빨리 잡아낸다.
- 재생 절차:
  1. `pending-queue.json`을 큐에 쌓인 순서대로 순회.
  2. `create_issue`/`create_comment`처럼 신규 생성 항목은 충돌 여지가 없으니
     바로 전송. `create_issue`가 성공해 실제 서버 ID를 받으면, 큐에 남은
     항목 중 같은 임시 ID를 참조하던 것들을 실제 ID로 치환한다.
  3. `update_field`/`delete_issue`처럼 기존 리소스를 건드리는 항목은 전송
     직전 서버에서 해당 이슈의 현재 `updated_at`을 조회해 큐의
     `baseUpdatedAt`과 비교.
     - 같음(그 사이 아무도 안 건드림) → 전송, 큐에서 제거.
     - 다름(충돌) → 전송하지 않고 `conflicts.json`으로 이동, 로컬 캐시 값은
       사용자가 결정할 때까지 유지.
  4. 재생이 끝나면 사이드바를 다시 fetch해 캐시를 최신화.

## 수동 병합 화면

- 충돌이 하나 이상 있으면 사이드바 footer에 "충돌 N건 · 확인 필요" 배지가
  뜬다. 클릭하면 기존 `editmodal` 패턴을 재사용한 새 창이 열린다.
- 항목별로 실제로 값이 다른 필드만 선택지를 보여준다(우연히 같아진 필드는
  자동 스킵):

  ```
  이슈: "로그인 버그 수정"
    우선순위:  [내 변경: 높음]   vs  [서버 값: 긴급]   ( ) 내 값 유지  ( ) 서버 값 사용
    [해결 완료]
  ```
- **삭제 충돌**(오프라인 중 삭제 요청했는데 그 사이 서버에서 수정됨): "그래도
  삭제" / "삭제 취소, 서버 값 유지" 두 선택지.
- **대상 소멸**(오프라인 중 수정하려던 이슈가 그 사이 삭제됨): "이 항목은
  서버에서 삭제되었습니다" 안내 후 "로컬 변경 폐기"만 가능.
- 사용자가 선택을 마치면 그 결과를 API로 전송하고 `conflicts.json`에서
  제거, 배지 카운트를 갱신한다.

## 엣지 케이스

- **오프라인 중 앱 종료 후 재시작**: `pending-queue.json`이 남아있으므로
  다음 실행 시에도 큐가 유지되고, 서버가 살아있으면 시작 직후 재생이
  진행된다.
- **댓글 대상 이슈가 오프라인 생성 임시 이슈**: 위 임시 ID 치환 순서를
  지키면 자연히 해결됨. `create_issue` 실패(네트워크 계속 끊김) 시에는
  하위 큐 항목들도 재생을 미룬다.
- **레이트 리밋(429)**: 기존 `send_retrying`의 지수 백오프 로직을 재생
  경로에도 그대로 적용한다.
- **큐가 비정상적으로 커짐**: 개인용 도구 특성상 발생 가능성 낮지만, 안전장치로
  큐 길이가 일정 임계치(예: 200건)를 넘으면 사용자에게 경고만 표시(자동 삭제
  하지 않음).

## 테스트

기존 컨벤션대로 순수 로직 분리 후 단위 테스트 (vitest / cargo test):

- **큐 적재/재생 순서**(Rust): 네트워크 실패 시 큐잉되는지, 4xx는 큐잉되지
  않는지, 재생이 큐 순서를 지키는지.
- **임시 ID 치환**(Rust): `create_issue` 성공 후 하위 큐 항목의 `targetId`가
  올바르게 치환되는지.
- **충돌 판정**(Rust): `baseUpdatedAt` vs 재생 시점 서버 `updated_at` 비교
  로직, 같음/다름/대상 소멸 세 케이스.
- **병합 화면 필드 diff**(TS): 실제로 다른 필드만 노출되는지, 선택 결과가
  올바른 페이로드로 변환되는지.
